The 3D Prints Portal design system (version **1.8**) is fully implemented and the app has shipped as 1.0.0. Thank you for 1.8: GAP-060 is confirmed and generalised into the third-party-renderer rule, and GAP-061's opaque badge base is in. You were also right to push back on my 1.7 measurement — I had measured a badge on a hovered row and never on a selected one, which is exactly where the composite failed.

This round is much bigger than the last few, and it is a different kind of round. The owner has now walked through the finished app with real data (83 prints, 10 klanten, two years of history), and I reviewed every screen beside them at desktop and phone width in both themes. **26 gaps**, GAP-062 to GAP-087, nearly all of them about how the system behaves at real size rather than about a missing token or state.

Two are already built as approved placeholders (GAP-062 and GAP-063) and marked `ds-gap:` in the code; they need your verdict. The other 24 are untouched.

## What is different about this round

Most of the system has only ever been seen at example size. At real size three things show up repeatedly, and they are worth deciding as principles before the individual gaps:

1. **Screens that grow without limit.** The klant strip on the dashboard (GAP-067), Openstaand (GAP-080), Deel-links (GAP-081). Each was specified for a handful of rows and now renders everything: Openstaand is 6106px and about 90 rows in one page. Please say how the system handles a list that keeps growing: paging, collapsing, a cap with a count.
2. **Space spent in proportion to value.** The 3D viewer takes roughly 1090x830 on a 1360px window and the same frame when there is no model at all (GAP-064); the klant strip takes 350px before the first print (GAP-067); the order block nests three rounded cards (GAP-074). Meanwhile the main action on the print detail sits below the fold.
3. **The customer-facing page is the least finished.** It is the only screen people outside the studio ever see, and it shows them the link's internal label (GAP-077), never says how to pay (GAP-078) and shows no pictures of what they ordered (GAP-079).

## Priority

**First, the share page: GAP-077, GAP-078, GAP-079.** GAP-077 is close to a privacy bug: the label is written as an internal note and rendered to the customer, so this instance currently shows klanten strings like "PR 8 review". GAP-078 means the page names an amount owed and gives no way to pay it.

**Then the print detail: GAP-064 and GAP-074**, which together are most of the screen the operator works on all day.

**Then the two structural ones: GAP-066** (no sort and no status filter on a paged list of 83) **and GAP-063** (the sidebar).

The rest can follow in any order. GAP-085 (video) and GAP-086 (several models) are the only two that need a genuinely new component.

For each gap:

1. **Decide.** Resolve it, merge it with another gap, or reject it with a reason. Ask me if a gap needs a product decision — several here do, and I have said so in the entry.
2. **Resolve within the system.** Prefer existing tokens and components. Add a new token or component only if it is genuinely needed, and name it consistently. Don't rename or remove existing tokens unless the gap requires it; list every breaking change.
3. **Deliver completely.** Values for both themes, all states, phone and desktop layouts where relevant, Dutch copy, and contrast ratios for any new colour pair (WCAG 2.2 AA).
4. **Update the hand-off deliverables:** `tokens.css` (and JSON), `components/bundle.css`, the affected component specs and screens, the copy deck and the contrast report.
5. **Keep READMEs complete** and **every class a preview uses defined in `bundle.css`**, as in 1.6 through 1.8.
6. **Check the long screens at real size.** Several gaps are invisible in a short preview: please draw Openstaand with about 90 rows, the dashboard with 20 klanten, and the print detail at 360px.
7. **Say what you want measured.** Where a decision depends on a number I can get from the running app (a real ratio, a rendered height, how often a state occurs), ask and I will measure it rather than guess. That is how GAP-061 went wrong in 1.7.

Finish with a **changelog for the new version (1.9)**:
- a table `GAP-### → resolved / confirmed as built / merged into GAP-### / rejected (reason)`;
- new tokens, changed tokens, new or changed classes, components and screens;
- breaking changes, if any.
