The 3D Prints Portal design system (version **1.3**) is now being implemented. The developer found the gaps below while building milestone 6 (costs, Spoolman, payments, bulk actions and Instellingen) and while checking v1.3. Please update the design system to resolve them.

For each gap:

1. **Decide.** Resolve it, merge it with another gap, or reject it with a reason. Ask me if a gap needs a product decision.
2. **Resolve within the system.** Prefer existing tokens and components. Add a new token or component only if it is genuinely needed, and name it consistently with the existing scheme. Don't rename or remove existing tokens unless the gap requires it. If you must, list every breaking change.
3. **Deliver completely.** Give values for both light and dark themes, all states, phone and desktop layouts where relevant, Dutch copy, and contrast ratios for any new colour pair (WCAG 2.2 AA).
4. **Update the hand-off deliverables:** `tokens.css` (and JSON), `components/bundle.css`, the affected component specs and screens, the copy deck and the contrast report.
5. **No raw values in screens.** The app may only use tokens and the classes in `components/bundle.css`; it cannot copy inline `style="…"` values (sizes, widths, opacities, z-index, timings) from the previews. Every value a screen needs must exist as a token or a class. v1.3 cleaned the dashboard, print detail and asset list; please do the same for PaymentPanel, CostBreakdown, CostOverrideDialog, SpoolPicker, MoneyDisplay, ScreenSettings, and the screens for M7 (ScreenOutstanding, ScreenInvoiceExport, ScreenInvoices) so the next milestone does not hit the same problem.

**Priority:** GAP-033 and GAP-029 first; they affect daily use.

Product decisions taken since v1.3 that affect the design (use them when resolving the gaps):

- **Repeat orders ("Nabestelling").** A print (project folder) has one or more orders. Order 1 always exists. An order holds its own items (a G-code file or 3MF plate, each with its own "Aantal keer geprint" for that order; the same file can be reprinted in a later order), its own Verkoopprijs, payments and write-off, and from M7 its own invoice line. New files join the newest order while that order has no price, payment or write-off; otherwise they wait until the owner makes a Nabestelling and ticks them in. Files stay in the same project folder.
- **Payments.** A payment can be at most the open remainder (overpayment is refused). "Betaling ongedaan maken" (Admin only) reverses the most recent payment of the order; undone payments stay in the history with who and when.
- **Tag colours** are the ten palette keys from v1.3 or none.
- **Settings already in the app:** Algemeen (re-index, theme), Prijzen (Standaardmarge), Bedrijfsgegevens, Klanten (Niet factureren), Spoolman status. Printer profiles (name, aliases, timelapse prefixes, watts), the electricity tariff (€/kWh) and the default price per kg per material exist in the API but have no screen yet (GAP-033).
- **Bulk actions in the app:** Markeer als betaald, Tags (tri-state), Verwijderen. "Spoel toewijzen" and "Prijs instellen" wait for their dialogs (GAP-034). The API returns a result per print.

## GAP-029 [open] Popovers and menus have no stacking level
- **Type:** missing token
- **Found while:** M5 with v1.3, checking the dashboard and print detail in the browser
- **Where needed:** FilterBar "Tags" popover (ScreenDashboard), TagEditor popover above 480px (ScreenPrintDetail), later the BulkActionBar "Acties" menu and other Popovers; `frontend/src/prints/FilterBar.tsx`, `frontend/src/prints/TagEditor.tsx`
- **What is missing or wrong:** `.pp-pop` has no `z-index` and the design system has no stacking tokens (only raw values inside `bundle.css`, e.g. the phone `.pp-tagpop` at 50). An absolutely positioned popover is painted under content that comes later in the page and is itself positioned: the PrintCard (`.pp-print` is `position:relative`) covers the FilterBar Tags popover, and the Viewer3D would cover a TagEditor popover. App code may not choose a `z-index`.
- **Why it matters:** the FilterBar Tags popover is partly hidden behind the first row of print cards, so tags below the first one cannot be ticked with the mouse (keyboard still works).
- **Proposal:** stacking tokens, e.g. `--z-sticky` 10, `--z-popover` 30, `--z-overlay` 50, and `.pp-pop{position:absolute; z-index:var(--z-popover)}` (or a `.pp-pop.floating` variant). Until then the TagEditor above 480px opens in the page flow under the tags (it pushes the content down instead of floating); at 480px and below it is the design system's bottom sheet.
- **Blocked:** a floating TagEditor on desktop and a FilterBar Tags popover that is not covered by the cards. Filtering by tags still works through the keyboard and the phone Filters sheet.
- **Owner decision (2026-10-06):** wait for the design system, no placeholder.

## GAP-035 [open] Screens for several orders in one print (Nabestelling)
- **Type:** missing screen
- **Found while:** M6, owner decision on repeat orders
- **Where needed:** ScreenPrintDetail, PaymentPanel, AssetListItem, PrintCard/PrintRow status, CostBreakdown, copy deck
- **What is missing or wrong:** the owner decided that a print can have several orders: when a klant wants more of a project or a part broke, a "Nabestelling" gets its own items (files or plates with their own times printed; the same file may be reprinted), sale price, payments, write-off and later invoice line. Order 1 is the current single order. Nothing in the design system covers: the list of orders on the detail page, a PaymentPanel and CostBreakdown per order, the "Nabestelling maken" flow (tick files, times printed per order), files that are not in any order yet (new files after order 1 was priced or paid), and how the dashboard summarises several orders (least settled status, total and open amount).

Voeg het toe aan een nabestelling."; PrintCard shows the summed price and the least settled badge, with "{n} bestellingen" in the meta line.

- **Temporary placeholder approved:** no
